# 語より先に指示対象を固定する

書く前に指す対象と役割を確定し、決めた名前だけで書くための手順。名前を先に置いて対象を後から当てはめたり、書きながら短い呼び名や作業ラベルを作ったりすると、日本語文、設計要素、コード識別子の間で意味がずれて読み手に伝わらなくなるためである。

## 常に守る3つの基準

1. **本文より先に対象と名前を固定する**：対象文書では対応表を別ファイルか別ターンで独立して保存してから本文を書く（本文の先頭に表を置くだけでは先に固定したことにならない）。返信、進捗チェックリスト、PR の説明、依頼文のような短い物ではファイルに保存せず、書き始める前に指す物と使う名前を会話の中で先に決めてから書く。
2. **骨組み、見出し、表、チェックリスト、結論に作業ラベルや1語の総称を置かない**：未整理の作業を抽象名詞で包んだ作業ラベル（「観測をまとめる」など）や、1語の総称（「作業者」「相手」「動く所」「対象」など）を使わない。使いたくなったら具体対象と役割を表に書けるか試し、書けなければ捨てて対象と内容を具体的に書く。
3. **新しい呼び名と短縮語を作らない**：名前のある物はそのままの名前で書き、2回目以降も同じ名前を繰り返して別の語や「所」「場所」「経路」「側」「もの」のような語（1語の総称を名詞の後ろに付けた形を含む）に言い換えない。複数の物を指すときも名前を並べて書き、並べきれないときは選ぶ条件を文で書く。名前の無い物は何が何をするかを文で書く。コードの識別子、ファイル名、状態名、条件名、事象名、型名、メソッド名、boolean 名、画面に出す名称のように新しい名前が本当に要るときだけ、対応表で具体対象と役割を先に確定してから付け、初出で「X とは〜を指す」と定義する。

## 適用範囲

判断に迷う場合は適用する。

- **対応表を独立保存して書く対象文書**：
  - 設計資料、要求からの設計、調査報告、原因切り分け案、対策案
  - 自分で新しい名前を決めるとき（ファイル名、公開仕様、状態名、条件名、事象名、値や記録の型名、メソッド名、boolean 名、画面に出す名称。依頼に「命名」の語が無くても該当する）
  - ユーザーが示した推論の順序を短い見出しやラベルにまとめようとするとき
- **会話の中で対象と名前を先に決めて書く短い物**（ファイルへの保存は不要）：
  - 返信、進捗チェックリスト、PR の説明、issue、ほかのスレッドや担当への依頼文
- **対象外**：
  - ユーザー原文の引用、単純な機械編集、既存名だけを再利用する箇所、定型出力、雑談、確立した用語だけで書ける短文
  - 対象、役割、名前、意味を変えない表現だけの推敲（現在進行中の工程をそのまま続ける）

## 使ってよい名前と造語が出やすい箇所

- **使ってよい名前を探す先**：プロジェクト指示、skill、コード・設定・コマンド、製品の画面、製品やツールの説明の原文、用語集、u1 さんの発言、公的名称や定着した専門用語、一般的な日本語。
- **ほかの Claude の文は探す先に含めない**：コーディネーター、ほかのスレッド、サブエージェントが書いた依頼文、返信、進捗チェックリスト、PR、文書、過去の対応表にあることだけを既存名の根拠にしない（ほかの Claude の造語が既にある用語のように広がるのを防ぐため）。受け取った文に上の探す先に無い呼び名があっても引き継がず、元の対象の名前を並べるか具体的な文に直す。
- **同じ物を言い換えない**：1つの物や仕組みは、返信、表、資料をまたいでも同じ名前を繰り返して書く（前の返信で「通知」と書いた物を次の返信の表で「知らせ」に替えるように別の語へ言い換えると、別の物に見えてしまうため）。
- **表の列見出し、節の見出し、題名、進捗チェックリスト**：短い名詞で埋めようとすると「作業者」「相手」「動く所」「対象」のような1語の総称や造語、「止める2文」のような短縮語が出やすい。列や行に入る中身を具体的に表す語句にし（例：Codex と Antigravity が並ぶ列なら「実装やレビューを依頼する AI」）、短く言い表せなければ表をやめて物ごとに1文で書く。
- **複数の物をまとめて指すとき**：Codex、Antigravity、grok、コーディネーター、スレッドのように名前がある物を複数指すときに、ひとまとめの呼び名（「動き手」「担い手」など）を作らず、その都度名前を並べて書く。「所」「場所」「経路」「側」「もの」のような語を名前のある物の代わりに使わず、1語の総称を名詞の後ろに付けた形（「実行経路」「残りの経路」など）や「読む所」「届かない場所」のような言い方も使わない（例：「poteto-mode を読まない所」とまとめず、「コーディネーター、毎週・毎時の処理のスレッド、general-purpose のサブエージェント」と書く）。名前が多くて並べきれないときは、並べる物を選ぶ条件を文で書く（例：「プロジェクト指示が届かないサブエージェントと、u1macmini で動く Codex、Antigravity、grok」）。
- **作業や行為を表すとき**：調査、修正、確認、依頼、比較のような一般的な名詞か動詞の文で書き、動詞をそのまま名詞にした呼び方（「読み」「調べ」「確かめ」「直し」など）は使わない。資料の中だけで付けた案の番号や作業上の呼び名（「方針2」「型」「回答欄」など）だけで物を呼ばず、中身を普通の言葉で書く。

## 短い物を書く流れ（返信、進捗チェックリスト、PR の説明、依頼文）

1. 書く前に、本文、題名、見出し、表の列見出し、チェックリストの行で触れる対象と、上の「使ってよい名前を探す先」から取った名前を会話の中で先にそろえる（ファイルには保存しない）。本文やチェックリストで何度も触れる物の名前を必ず入れ、2回目以降も同じ名前を繰り返して使う（1回名前を並べた後に「所」「場所」「経路」「側」「もの」で受け直さないため）。
2. そろえた名前と具体的な文だけで書き、同じ対象が出てくるたびに決めた名前を繰り返す。表の列見出しや複数の物をまとめる箇所で新しい呼び名や短縮語を置きたくなったら、名前を並べるか、並べる条件を文で書くか、表をやめて文で書く。
3. 送る前に、本文、題名、見出し、表の列見出し、チェックリストの各行を含めて、先にそろえた名前と一般的な日本語だけで書けているかを確認し、どこにも無い呼び名、短縮語、名前のある物を言い換えた「所」「場所」「経路」「側」「もの」があれば書き直してから送る。

## 対象文書で対応表を先に作る流れ

ユーザーの質問への短い回答や作業の受領は、対応表より先に返してよい。

### 1. 7列の対応表で対象と役割を確定する

本文を書く前に、次の7列をこの順で作る。

```markdown
| 出典 | 目的 | 具体対象 | 役割 | 前後関係 | 候補語 | 初出定義 |
```

- **具体対象と役割を先に埋める**：両方が埋まるまで、候補語と初出定義は空欄のままにする（先に名前を置いて対象を後付けするのを防ぐため）。
- **役割は7つから選ぶ**：`開始条件`、`状態`、`事象`、`値`、`記録`、`目的`、`手段` のいずれかにする。同じ名前が複数の役割を指すときは行を分ける。
- **前後関係は原文の順序で書く**：ユーザーが示した推論や作業の順序（例：テスト → 切り分け → 対策）を原文の言葉で書く。役割は役割列にだけ書く。
- **表は1〜6行に収める**：超える場合は意味が変わる境界で表を分ける。
- **実物で具体対象を確定する**：候補語列を隠しても具体対象列だけで何について述べるか分かることを確認してから、候補語を埋める。設定は実際の識別子、操作は実行する人やプログラムと操作対象、コピーや配置は使うコマンド・スクリプトとコピー元・配置先を実物で確認する。過去の説明文を写すだけで確定にせず、特定できない箇所は未確認として残す。
- **既存の表を再利用するとき**：同じ文書の修正でも別の報告でも、その表を読み、今回の対象、役割、前後関係と照合する。一致する行は残し、追加や変更がある行だけを対象から確定し直す（表の名前に今回の対象を合わせない）。

### 2. 候補語と初出定義を決める

- まず上の「使ってよい名前を探す先」にある既存名や具体対象の記述で伝わるかを確認し、伝わるならそれを候補語に置く。新しい呼び名や短縮語は作らない。
- コードの識別子、ファイル名、状態名、画面に出す名称のように新しい名前が本当に要るときだけ、具体対象と役割を確定したうえで必要性（新しい対象の区別、コードの命名規則への適合、ユーザー指定の改名など）を確認し、初出定義欄に「X とは〜を指す」と書く。定義できることだけを採用理由にせず、必要性や定義を説明できない語は導入せず具体対象の記述を使う。

### 3. 対応表を本文より先に独立保存する

- スクラッチパッドの `referent-tables/referent-table-<slug>.md` に保存する（スクラッチパッドが無ければ `tmp/referent-tables/`。ディレクトリが無ければ作る）。保存を終えてから本文に着手する。
- 再利用する表の内容に変更が無ければ再保存しない。行を更新したときは、更新した表を保存してから本文に反映する。
- 書き込みできない環境ではファイルを作らず、同じ7列を本文より前のターンか作業の文脈内で先に確定してから本文を書く（保存できないことを理由に質問や計画を止めず、上位指示を越えてファイルを作らない）。

### 4. 対応表に沿って本文を書く

- 保存する文書とユーザーへの最終回答の両方で、対応表に載った語だけを中心語彙にし、述べる対象、操作、条件を表の具体対象と一致させる。最終回答を短くまとめるときも、表で確認した識別子、操作名、操作対象を残し、リンク先や途中の報告を読まないと対象が分からない省略にしない。
- 文書や最終回答に必要な対象、操作、条件が表から抜けていたら、先に行を確定・保存してから本文に書く。
- 日本語文、設計要素、コード識別子の3つで同じ対応を保つ（例：「履歴量が 250K に達する」は開始条件として条件名、「自動要約が始まる」は事象として事象名・メソッド名、「自動要約実行中」は状態として状態名にし、別役割は別名にする）。

## 複数担当での共有と永続保存

### 複数担当で共有するとき

文書作成の依頼元と文書を書く担当が作業の前に確認する。対応表は担当ごとに作らず、依頼元のセッション単位で共有する。

- 管理元は依頼元とし、書き込みできる環境では依頼元のスクラッチパッドの `referent-tables/<CLAUDE_CODE_SESSION_ID>.md` に保存する。書き込みできない環境や別スレッドへの依頼では、表の内容を依頼文で共有する。
- 同じファイルで複数の文書を扱うときは、どの文書の対応かが分かるよう文書ごとに表を分ける。行を再利用するときも今回の対象、役割、前後関係を確認する。
- 文書を書く担当は、渡された保存先の表（書き込みできない環境では同じ依頼で共有された最新の表）を文書を書く直前に読み直し、そこに載っている語だけを中心語彙にする。別セッションの表を取り込まないよう、渡された表以外を自分で探さない。
- 表の保存先も内容も渡されていないときは、新しい語を作らず依頼元へ共有を求める。
- 文書を書く担当は表を直接編集せず、新しい名前も作らない（更新が分岐するのを防ぐため）。表に無い対象が出たら具体対象の記述を依頼元へ返し、依頼元が表を更新する。

### 永続保存するとき

ユーザーの明示的な依頼、タスクの受入条件、後続のレビューで保存先の確認が必要な場合だけ永続保存する。理由と所有する成果物を表の先頭に書き、特定の文書に属する表はその文書と同じディレクトリ、リポジトリ全体の表は `docs/referent-tables/` に保存する。共有先や永続保存先に置く場合も、上の7列、命名条件、本文前の保存、下の問題時の対処に従う。

## 問題が起きたときの対処

- **対応表なしで本文を書き始めたとき**：後付けで表を足して続けず、本文を破棄し、対応表を独立して先に作り直してから本文を書き直す。
- **表の行の誤りや造語の指摘を受けたとき**：対象や役割の取り違えを指摘されたら、補足説明を足すのではなく該当行を書き直してから本文の該当箇所を書き直す。短い文で造語や短縮語を指摘されたら、その語を文から消し、対象の名前を並べた文か具体的な文に書き直す。
- **この skill の参照先が開けないとき**：同じ7列（出典、目的、具体対象、役割、前後関係、候補語、初出定義）で対象を先に確定し、現在の環境に従って保存または会話内で確定してから着手する。
- **保存先を作成できないとき**：リポジトリのルートに代替保存しない。許可済みの一時ディレクトリがあればそこに保存し、保存の承認が不可欠な場合だけ必要な保存先と理由を示して確認する。
