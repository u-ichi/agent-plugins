# skill の付け直しと呼び直しの検証結果

この文書は、Claude Code の不具合によって、プロセスの再開をはさんだ compact の後に Skill ツールで呼んだ skill の本文が付け直されない問題について、仕組みの確認、呼び直しの効果の測定、およびこの plugin の hook の動作確認をまとめた記録である。実際の3つの会話での観測、skill 以外の物の比較、および会話の記録での確認手順は [README.md](../README.md) にある。

## この検証で確かめたこと

1. Claude Code の compact は、どの条件で skill の本文を付け直し、どの条件で落とすか。
2. skill の本文が付け直された場合と付け直しから落ちた場合で、呼び直しを求める処理は何を回復するか。
3. この plugin の hook は、プロセスの再開をはさんだ実際の会話の記録で、付け直されなかった skill だけを求め、付け直された skill や呼び直し済みの skill を求めないか。

## 仕組みの確認（Claude Code 2.1.330）

project の skill（各 14,408 文字を複数、および 120,162 文字の大きい skill）、plugin の skill、built-in の skill（15,190 文字）を Skill ツール（一部はスラッシュ呼び出し）で呼んでから `/compact` を実行し、会話の記録 JSONL とモデルの応答を確認した。

### 同じプロセスの中の compact

- 同じプロセスの中で `/compact` を実行すると、Skill ツールで呼んだ skill の本文は付け直される。project、plugin、built-in のいずれでも付け直しの扱い、順序、上限は同じであった。
- 記録の形：compact の境目（`compact_boundary`）の数行後に `attachment.type` が `invoked_skills` の行が付き、`skills[]` の各要素に `name`、`path`、`content` が入る。モデルへ渡される枠の文では、これらは以前のターンで呼ばれた skill であり再実行せず継続的な方針だけ従うよう注意が添えられ、各 skill は `### Skill: <name>` と `Path: ...` の後に本文が続く。project と plugin の skill の `content` の先頭には `Base directory for this skill:` の行が付くが、built-in の skill には付かない。
- 1つの skill の上限：120,162 文字の skill を最後に呼んで compact すると、`content` は先頭の `Base directory for this skill:` 行を含めて 20,000 文字で切れ、末尾に切り詰めの印（`[... skill content truncated for compaction; use Read on the skill path if you need the full text]`）が付いた。2回続けて compact しても同じ 20,000 文字のままであった。
- 全体の上限：9個の skill を呼んで compact したとき、付け直されたのは新しい順に 8個（計 87,633 文字）だけであった。9個目を足すと 102,041 文字になって上限を超えるため、古く呼んだ skill から通知なしで落ちた（一部が省略されたという通知は出なかった）。測定結果から、1つの skill は 20,000 文字（約 5,000 トークン相当）、全体は約 100,000 文字（約 25,000 トークン相当）を文字数基準で判定していると見られる。

### プロセスの再開をはさんだ compact

- skill を呼んだプロセスを終了し、`claude -p --resume <セッションID>` の別プロセスで `/compact` を実行すると、`invoked_skills` は付かなかった。skill の本文は文脈に残らず、要約の中の引用だけになった。
- 同じ実験で、Read ツールで読んだファイルは `file` として付け直され、`SessionStart`（`compact`）の追加の文脈も届いた。この結果から、呼んだ skill の一覧はプロセス内のメモリにだけ保持されていると分かる。
- 実際の3つの会話（Claude Code 2.1.328、2.1.330、2.1.331）で同じ欠落を確認した詳細は [README.md の「観測結果」](../README.md#観測結果) を参照。

## 呼び直しの効果の測定

### 実施時期と方法

- 実施時期と環境：2026-11-24 06:40〜08:55 JST（UTC 2026-11-23 21:43〜23:53）、Claude Code 2.1.330。モデルは `sonnet`（`claude-sonnet-5-5`）を中心とし、一部の場面で `opus`（`claude-opus-5-5`）と `fable`（`claude-fable-5-2`）も実行した（記録の `message.model` で確認した）。有効な実行は合計 101 回である。
- 共通の前提：すべての実行で `SessionStart`（`compact`）にプロジェクト指示にあたる文を入れ直したうえで、skill 側の扱いによる差だけを測った。最初のメッセージで実物の skill 群を順番に Skill ツールで呼ばせた後、skill の中身を使わない別の作業（生成された Python のコードを複数ファイル Read して共通関数にまとめる作業）を挟んで compact を起こし、最後のターンで PR まわりの仕上げのファイル6つを書かせた。
- 比べた実行：
  - 何も入れない実行（Claude Code 自身の付け直しだけ）
  - 呼び直しを勧める文を入れるだけの実行（`SessionStart`（`compact`）で「付け直された skill は今も従う手順であり、全文が要るときは Skill ツールで呼び直す」という英語 236 文字の1文を追加）
  - 呼び直すまで tool を止める実行（compact の前に呼んだ skill を記録から全部拾い、`PreToolUse` で `Skill`、`Read`、`ToolSearch`、`Glob`、`Grep` 以外を止め、拾った skill を全部呼び直すと解除）
  - compact を起こさない実行（比較用の基準、`sonnet` N=5）
- 数え方：出力されたファイルとコマンドから機械的に検査できる 30 個の規則の達成数を数えた。うち 1個は簡易判定に見落としがあるため（手作業の照合で 1件）、30 個と 29 個の両方で集計した。

### 同じプロセスの中で上限に収まる場合（実物の skill 6つ、計 42,846 文字）

実物の skill 6つ（合計 42,846 文字、最大の1つは 15,846 文字）を呼ぶ場面で、`sonnet` は auto compact（`CLAUDE_CODE_AUTO_COMPACT_WINDOW=250000`、`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=70`、実際の発動は 159,000〜165,000 トークン）、manual compact、2回 compact の3場面を各実行 N=5（計 45 回）、`opus` と `fable` は auto compact を各実行 N=3（各 9 回）、compact を起こさない実行を `sonnet` N=5 で走らせた。

- 付け直しの確認：境目 78 回（auto 33回、manual 15回、2回 compact 30回）のすべてで、6つの skill が全文のまま付け直された（切り詰め 0回）。実トークン数では約 3.3 万トークンあったが、文字数ベースの上限（1 skill 20,000 文字、全体約 100,000 文字）に収まるため切られなかった。
- 満たした規則：`sonnet` の3場面を合わせた各実行 N=15 の平均（29 規則）は、何も入れない実行 28.3、呼び直しを勧める文を入れるだけの実行 28.4、呼び直すまで tool を止める実行 28.4 で差がなかった（並べ替え検定 p=0.87）。compact を起こさない実行（N=5）は 28.8 であった。`opus` と `fable` の auto compact（各実行 N=3）は全実行で 30/30 であった。
- 自分で呼び直した回数：何も入れない実行と呼び直しを勧める文を入れるだけの実行では、最初の境目より後にモデルが自分で skill を呼び直したり読み直したりした回数は 0回であった（各 21 回中）。
- 呼び直すまで tool を止める実行が回復したもの：この場面では何も回復しなかった。上限に収まる場面と上限を超える場面を合わせた全測定で呼び直させた 354 回のうち 343 回は、すでに `invoked_skills` に載っていたため Claude Code が本文を足さず、以前に読み込んだ旨の 170 文字の一文だけを返した。本文が入り直した 11 回は、すべて付け直しから落ちていた skill（下の上限を超える場面）であった。
- 別の確認（約 19,000 文字の skill を 6つ呼んで `/compact` し、付け直しが 5つ・計 95,973 文字になって 1つが落ちた状態）：落ちた skill を呼び直すと本文 19,194 文字がそのまま入ったが、付け直しに残っている skill を呼び直すと 170 文字の一文だけが入った。
- 要約の中身：6つの skill を使う場面の 60 回の最初の要約（平均 10,361 文字）を確認したところ、検査対象の規則の手がかりはほとんど残っていなかった（公開リポジトリでの参照記法に関する言及だけが 34 回に入っていたが、チェックリストの書式や見出し形式などの大半の規則は 0〜6 回）。そのため、skill の本文が付け直しから落ちると規則はモデルの記憶に残らない。

### 全体の上限を超えて skill が落ちる場合（実物の skill 18個、計約 106,000 文字）

上の 6つの skill に別の実物の skill 12個を加えて計 18個（本文と見出しの合計約 106,000 文字）を固定の順で呼び、作業の後に manual compact を行って同じ仕上げの依頼を出した。`sonnet` は各実行 N=5（15 回）、`opus` と `fable` は各実行 N=3（各 9 回）である。

- 付け直しの確認：境目 33 回中 32 回で、最初に呼んだ skill だけが落ち、残りの 17個が全文で付いた。残り 1回（`opus` の呼び直しを勧める文を入れるだけの実行）は、モデルが compact の前に最初の skill を呼び直していたためそれが残り、代わりに別の2つの skill が落ちた。

| モデル | 実行 | N | 実行ごとの達成数（/30） | 平均 /30 | 平均 /29 |
| --- | --- | --- | --- | --- | --- |
| sonnet | 何も入れない実行 | 5 | 24, 25, 30, 24, 25 | 25.6 | 25.4 |
| sonnet | 呼び直しを勧める文を入れるだけの実行 | 5 | 29, 28, 27, 29, 30 | 28.6 | 28.4 |
| sonnet | 呼び直すまで tool を止める実行 | 5 | 27, 28, 29, 29, 29 | 28.4 | 28.4 |
| opus | 何も入れない実行 | 3 | 30, 25, 25 | 26.7 | 26.3 |
| opus | 呼び直しを勧める文を入れるだけの実行 | 3 | 30, 30, 30 | 30.0 | 29.0 |
| opus | 呼び直すまで tool を止める実行 | 3 | 30, 30, 30 | 30.0 | 29.0 |
| fable | 何も入れない実行 | 3 | 30, 30, 30 | 30.0 | 29.0 |
| fable | 呼び直しを勧める文を入れるだけの実行 | 3 | 30, 30, 30 | 30.0 | 29.0 |
| fable | 呼び直すまで tool を止める実行 | 3 | 30, 30, 29 | 29.7 | 28.7 |

- 落ちた規則の傾向：`sonnet` の何も入れない実行では 5回中 4回で、最初に呼んだ skill にしか書かれていない規則（チェックリストの形や参照の書き方など）がそろって落ちた。残り 1回はモデルが自分でファイルを読み直して 30/30 であった。`opus` の何も入れない実行でも 3回中 2回で同じ 5規則が落ち、1回は自分で読み直して 30/30 であった。`fable` の何も入れない実行は 3回とも自分でファイルを読み直して 30/30 であった。
- 回復の比較：`sonnet` では、呼び直しを勧める文を入れるだけの実行と呼び直すまで tool を止める実行が同程度に回復した（並べ替え検定は、何も入れない実行との差がいずれも p=0.063、両者の差は p=1.0。N=5 のため統計的に言い切る強さではないが、落ちた規則は最初に呼んだ skill に固有の規則にそろっていた）。
- 呼び直し回数と費用：

| モデル | 何も入れない実行（自分で読み直した回数） | 呼び直しを勧める文を入れるだけの実行（落ちた skill だけを呼び直した回数） | 呼び直すまで tool を止める実行（止めた呼び出し回数／呼び直した skill 数） |
| --- | --- | --- | --- |
| sonnet | 1/5 | 5/5 | 1, 1, 6, 6, 6 回／全 18 skill を 5/5 回 |
| opus | 1/3 | 2/3（残り 1回は compact 前に残っていた） | 1, 1, 1 回／全 18 skill を 3/3 回 |
| fable | 3/3 | 3/3 | 1, 1, 1 回／全 18 skill を 3/3 回 |

- 最後の境目以降の API 呼び出し回数と時間（`sonnet`）：API 呼び出しの平均は何も入れない実行 6.2 回、呼び直しを勧める文を入れるだけの実行 3.2 回、呼び直すまで tool を止める実行 5.0 回であった。所要秒の平均はそれぞれ 123 秒、69 秒、90 秒であった。
- 集計から外した実行：試走 1回（最後の依頼のターンの先頭で auto compact が起きたため場面として無効）と、場面の第 1 版 4回（依頼文の前提が不足していた版）は 101 回の集計に含めていない。

### この測定から採用した設計

すでに `invoked_skills` に付け直された skill を呼び直させても本文は入り直さず（170 文字の一文だけ）、呼び出し回数だけが増える。本文が回復するのは付け直しから落ちていた skill を呼び直したときだけである。そのため、この plugin は `invoked_skills` を確認し、付け直されなかった skill だけについて呼び直しを求める作りにした。

## この plugin の hook の確認

- 実際の会話の記録を使った確認：compact が 2回起き、その間にプロセスの再開が 5回あった実際の会話の記録（約 1,600 行の JSONL）をこの plugin の hook に読ませた。
  - 1回目の compact の直後の状態では、付け直されなかった 2つの skill だけを求めた。
  - 2回目の compact の直後の状態では、付け直されなかった 3つの skill だけを求め、付け直されていた 2つの skill は求めなかった。
  - 呼び直した後の記録を読ませたときは何も出なかった。
  - 処理時間は 0.06 秒であった。
- 自動テスト：15 件のテストがあり、次のコマンドで実行する。

```sh
python3 -m unittest discover -s plugins/claude-compact-restore/tests
```

## 測れなかったこと・未確認・限界

- この plugin を入れた状態で、実際の会話の中で compact を起こす通し確認は未実施である。
- サブエージェントの会話での動作は未確認である（この plugin はサブエージェントの呼び出しを対象外としている）。
- Skill ツールで呼び直して本文を入れ直す方式と、hook の追加の文脈で本文を差し込む方式のどちらが手順に従いやすいかの比較は未実施である。
- 呼び直しの効果の測定では、プロセスの再開ではなく全体の上限（約 100,000 文字）を超えることで欠落を作った。1つの会話で 18 個の skill を呼ぶのは極端な前提であり、実際の会話で上限を超える頻度は測っていない。また、1つの skill が 20,000 文字を超えて途中で切られる場面（検証に使った実物の skill の最大は 16,312 文字）、上限を超える場面での auto compact や 2回 compact、skill を呼ぶ順番を変えた場合は試していない。
- 効果の測定で使った「呼び直すまで tool を止める実行」は、記録から拾った skill を全部呼び直させる検証用の hook であり、付け直されなかった skill だけに絞るこの plugin の実装とは動きが異なる。
- 規則の検査は機械的に確かめられる 30 個と PR まわりの仕上げ作業に限られ、文章の質やほかの作業の規則は測っていない。`opus` と `fable` は各 N=3 であり、差を言い切る強さはない。費用は呼び出し回数と所要時間で測り、金額は測っていない。

## 同じ検証をやり直す方法

### 仕組みと不具合の再確認

1. 同じプロセス内で Skill ツールを使って skill を呼び、`/compact` を実行する。会話の記録 JSONL に `attachment.type` が `invoked_skills` の行が付くことと、`skills[].content` の長さを確認する。
2. skill を呼んだプロセスを終了し、`claude -p --resume <セッションID>` の別プロセスで `/compact` を実行する。会話の記録 JSONL で `invoked_skills` が付くかどうかを確認する（記録の探し方は [README.md の「確認の方法」](../README.md#確認の方法) を参照）。

### この plugin の hook の再確認

1. `python3 -m unittest discover -s plugins/claude-compact-restore/tests` を実行する。
2. プロセスの再開をはさんだ compact 後の会話の記録 JSONL をそのまま hook に読ませ、compact の前に呼んだすべての skill のうち付け直されなかったものだけが返ること、呼び直し後の記録では何も出ないこと、処理時間を確認する。
