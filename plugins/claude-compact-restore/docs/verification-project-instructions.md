# プロジェクト指示の入れ直しの検証結果

この文書は、Claude Code の compact の仕様によって claude.ai のプロジェクト（Claude Projects）の「プロジェクト指示」の全文が会話から無くなる問題について、仕組みの確認と、compact の直後に全文を入れ直す効果および費用を検証した記録である。plugin 全体の概要と使い方は [README.md](../README.md) にある。

## この検証で確かめたこと

1. 会話の最初のメッセージに入れたプロジェクト指示の全文は、compact の後に原文のまま残るか。
2. `CLAUDE.md` や hook の追加の文脈など、Claude Code 自身が compact の後に付け直す物と何が違うか。
3. compact の直後にプロジェクト指示の全文を入れ直すと、ルール違反が減るか。費用はどの程度か。
4. 同じ測定で比べたほかの案（利用者の発言の原文を戻す、読んだファイルを読み直させるなど）に差が出るか。

## 仕組みの確認

### 最初のメッセージに入れたプロジェクト指示の扱い

- 環境と方法：Claude Code 2.1.330、モデル `sonnet`（`claude-sonnet-5-5`）、3回実行した。最初の利用者のメッセージにプロジェクト指示の全文（6,054 文字）を入れ、Bash と Read の作業を数回行った後に `/compact` を実行した。その直後に24項目について「原文のまま引用／言い換え／無い」で答えさせ、最初の利用者のメッセージが原文で残っているかも尋ねた。要約の中身は人が読んで分類した。
- 結果：
  - 3回とも、最初の利用者のメッセージの原文は会話に残らなかった。
  - 要約に残ったのは、その compact までの作業に関係した規則だけであった。
  - 規則に関係しない作業の後は、返信の形のルールの一部しか残らず、作業の進め方のルールなどは消えた。作業が規則に触れていた場合でも、残るのは言い換えであり、作業の中で触れなかったルールは消えた。
  - 要約の長さは 4,000〜7,000 文字であった。

### Claude Code が自分で入れ直す物との違い

Claude Code 2.1.330 で、compact の前後にどの文脈が残るかを確認した。

- `CLAUDE.md`、`@AGENTS.md`、`.claude/rules/*.md`、`CLAUDE.local.md`、`~/.claude/rules/*.md`、`--add-dir` で指定した `CLAUDE.md` は、compact の後に全部付き直る。付くのは compact の直後ではなく、次の利用者の発言のときである（auto compact では同じターンの中ですぐ付く）。入れ子の `CLAUDE.md` と `paths:` 付きの rule は `file` 扱いに変わり、付け直される最大5ファイルの枠を使う。
- system prompt は compact の前後で一字も変わらない（前後で同じ hash になる）。
- output style（`output_style_instructions`）と MCP の instructions（`mcp_instructions_delta`）は compact の直後に付け直される。
- 最初の利用者の発言、tool の結果（Bash の出力を含む）、画像（添付も Read も）は付け直されない。manual compact では最後の assistant メッセージだけ原文で残るが、auto compact では直近のメッセージも原文で残らない。

### hook の追加の文脈が残る条件と長さの上限

Claude Code 2.1.330 で hook の動作を確認した。

- compact の後に残るのは `SessionStart`（`source` が `compact`）の追加の文脈だけである。`startup` の `SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PostToolUse` の追加の文脈は compact で消える。
- compact の処理は `PreCompact`、要約の作成、`SessionStart`（`compact`）、`PostCompact` の順に進む。`PreCompact` の標準出力（終了コード 0）と `/compact` の引数は要約を作るモデルに届く（auto compact でも `PreCompact` の標準出力は届き、終了コード 2 は auto compact を止める）。
- 追加の文脈（`additionalContext`）は 10,000 文字までそのまま届き、10,001 文字以上は先頭約 2 KB のプレビューと全文のファイルのパスに置き換わる。この制限は `SessionStart`、`PreToolUse`、`PostToolUse`、`UserPromptSubmit` のいずれでも同じであった。

## 入れ直しの効果と費用の測定

### 実施時期と方法

- 実施時期と環境：2026-11-24 05:00〜06:30 JST（UTC 2026-11-23 20:00〜21:30）、Claude Code 2.1.330、モデル `sonnet`（`claude-sonnet-5-5`）。
- 実行の形：1場面を1プロセスの `claude -p --input-format stream-json` で実行し、依頼を1つずつ送った。N は同じ場面を別プロセスで走らせた回数である。manual compact は `/compact` を1通の利用者メッセージとして送り、auto compact は環境変数 `CLAUDE_CODE_AUTO_COMPACT_WINDOW=100000` と `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=72` で起こした。
- 設定の切り分け：基本の測定では `--setting-sources project` を使い、利用者の `~/.claude/rules`、出力スタイル、ほかの plugin の hook、および `CLAUDE.md` を外して、検証用の hook だけが文脈に入る状態にした。別に、利用者の既定の環境（`~/.claude/rules`、出力スタイル、plugin あり）でも同じ場面を測り直した。
- 場面：最初の利用者のメッセージに、測定用に作ったプロジェクト指示にあたる文（約 2,200 文字。背景の段落と機械的に検査できる15個の英語の規則）を入れた。15個の規則は次のとおりである。
  - 返信の最初の行が `---`、2行目が `Result:`、最後の行が `~ end ~`、最大 10 行、行末に `:` を置かない
  - 時刻は `HH:MM JST`、日付は ISO 形式、箇条書きは `* `、パスはバッククォート、作成するファイルは `outbox/m_*`
  - 「just/simply/basically」禁止、絵文字なし、ダッシュなし、「you/your」禁止、「task」禁止
- 手順：compact の前に短いシェル作業を5回行った（時刻・日付・パス・箇条書き・ファイル作成が出ない作りにした）。その後、`/compact`、ファイル2つを作って日付と時刻を報告する作業、小さい作業2回、2回目の `/compact`、もう一度の報告の順に進めた。
- 比べた実行：
  - 何も入れない実行
  - compact の直後に全文を入れ直す実行（`SessionStart`（`compact`）で規則の全文 2,389 文字を、「最初のメッセージは消えたが規則は続く」という1行の前置き付きで出力）
  - PreCompact で要約を作るモデルに指示する実行（`PreCompact` の標準出力 355 文字）
- 数え方：返信の本文、作成したファイル、ツール呼び出しの記録からすべて機械的に違反数を数えた。

### manual compact の結果（`--setting-sources project`）

compact 後の返信4本（報告1回目、小さい作業2本、報告2回目）における15規則の違反数である。

| 実行 | N | 実行ごとの違反数合計 | 平均 | compact 前の5返信の違反（基準） |
| --- | --- | --- | --- | --- |
| 何も入れない実行 | 12 | 21, 22, 4, 17, 20, 21, 4, 5, 20, 13, 17, 0 | 13.7 | 12回中 1件 |
| compact の直後に全文を入れ直す実行 | 6 | 1, 2, 0, 2, 2, 2 | 1.5 | 6回中 1件 |
| PreCompact で要約を作るモデルに指示する実行 | 6 | 2, 1, 2, 2, 1, 1 | 1.5 | 6回中 2件 |

- 何も入れない実行の違反の内訳（48返信中）：最初の行 `---` が 32件、2行目 `Result:` が 32件、最後の行 `~ end ~` が 28件、時刻が 22件、ファイル名が 16件、行末の `:` が 15件、箇条書き `* ` が 11件、「you/your」禁止が 5件、最大 10行・パス・日付が各 1件であった。禁止語「just/simply/basically」・絵文字・ダッシュ・「task」禁止はどの実行でも 0件であった。
- compact の直後に全文を入れ直す実行に残った違反はすべて時刻の規則（JST の時刻の隣に UTC の時刻を併記したもの）であった。時刻の規則を除くと、全文を入れ直す実行は 0件、何も入れない実行は平均 11.8件であった。
- 2回目の compact の後も傾向は同じであった（報告2回目の違反は何も入れない実行で 0〜8件、全文を入れ直す実行で 0〜1件）。全文を入れ直す実行では入れ直した文が次の要約の元になり、2回目の要約が15規則とも残した回数は 6/6 回であった。
- 1回目の要約が15規則を残した回数は、何も入れない実行で 2/12 回（ほぼ消えたのが 10/12 回）、PreCompact で指示する実行で 6/6 回であった。

### auto compact での結果（`--setting-sources project`）

ファイル 11個（各約 9,000 文字）を順に Read させて文脈を 72,000 トークンまで押し上げ、1〜3回の auto compact（`PreCompact` の `trigger` が `auto`）を起こした。

| 実行 | N | auto compact の回数 | 最初の compact より後の返信9本の違反数 | 報告2回の違反 |
| --- | --- | --- | --- | --- |
| 何も入れない実行 | 2 | 2、3 | 36、33 | 返信の形や時刻・ファイル名など 6〜8件ずつ |
| compact の直後に全文を入れ直す実行 | 2 | 1、3 | 2、2（時刻の規則のみ） | 時刻の規則の 1件ずつ |
| PreCompact で要約を作るモデルに指示する実行 | 1 | 3 | 2（時刻の規則のみ） | 時刻の規則の 1件ずつ |

auto compact は manual compact と違い、最後の assistant メッセージが原文で残らない。そのため何も入れない実行では返信の形の規則が後続のほぼ全返信で破られた（manual compact の何も入れない実行で違反が少なかった回は、原文で残った最後の assistant メッセージが見本になったと推測される）。

### 利用者の既定の環境との比較（manual compact）

`--setting-sources project` の環境と、利用者の既定の環境（`~/.claude/rules`、出力スタイル、plugin あり）で同じ場面を比べた。

| 環境 | 実行 | N | compact 後の返信4本の違反数 | 1回目の要約が規則を残した回数 |
| --- | --- | --- | --- | --- |
| `--setting-sources project` | 何も入れない実行 | 12 | 21, 22, 4, 17, 20, 21, 4, 5, 20, 13, 17, 0（平均 13.7） | 15規則とも残 2/12、ほぼ消えた 10/12 |
| `--setting-sources project` | compact の直後に全文を入れ直す実行 | 6 | 1, 2, 0, 2, 2, 2（平均 1.5、時刻の規則のみ） | 14規則以上残 3/6（hook 実行前のため同じ条件） |
| 利用者の既定の環境 | 何も入れない実行 | 15 | 1, 2, 1, 2, 2, 2, 18, 2, 2, 2, 0, 2, 2, 2, 19（時刻の規則を除くと 13回が 0、2回が 16 と 17） | 7規則以上残 13/15、0規則 2/15 |
| 利用者の既定の環境 | compact の直後に全文を入れ直す実行 | 6 | 2, 0, 1, 2, 2, 1（時刻の規則のみ） | 3/6 が規則をほぼ落とした |

- 測定されたこと：`--setting-sources project` では 12回中 10回で要約から規則がほぼ落ちたのに対し、利用者の既定の環境では 15回中 2回に減った。ただし落ちたときの被害は大きく（返信4本で 16〜17件）、全文を入れ直す実行はどちらの環境でも時刻の規則を除き 0件であった。
- 推測：既定の環境で規則が残りやすいのは、system prompt や rules の attachment があることで要約を作るモデルが規則を重要な物と扱うためと考えられる。どの要素（rules、出力スタイル、plugin）が効いているかの切り分けは未実施である。

### 費用

- compact の直後に全文を入れ直す実行：入れた文字数は 2,389 文字（記録上の `hook_additional_context` は 2,567 文字）で、文そのものは compact のたびに約 600 トークンである。compact 後の最初の応答の入力トークンは、何も入れない実行の平均 36,999（N=12）に対して 38,252（N=6）で、差は +1,253 トークンであった（要約が長くなった分を含む。1回目の要約は全文を入れ直す実行が平均 3,400 文字、何も入れない実行が平均 2,210 文字）。止めた呼び出しは 0回であった。
- PreCompact で要約を作るモデルに指示する実行：指示文は 355 文字だが、要約が約 4,600 文字長くなり、compact 直後の入力トークンが約 +1,800 トークン増えた。

### 実行記録の整合の確認（計 169 回）

この一連の測定（ほかの案の比較を含む計 169 回の実行）の記録をすべて確認した。

- compact の境目の数は、送った `/compact` の数とすべて一致した（auto compact は 1〜3回起きた）。
- 何も入れない実行の記録には hook 由来の attachment が 1件も無かった。全文を入れ直す実行では `hook_additional_context` が compact の回数だけ付き、ほかの hook が入れた文脈は 0件であった。
- `CLAUDE.md` などの `instructions` attachment は、利用者の既定の環境で実行した記録だけに付いていた。
- 場面の設計中に捨てた無効な実行（返信の形だけの規則だった最初の場面、文脈が増えず auto compact が起きなかった初期の試しなど）は集計に含めていない。

## 同じ測定で比べて補わないことにした物

同じ一連の測定でほかの案も比べた。次の4つは、この場面では何も入れない実行との差が出なかったため、この plugin では補わないことにした。

| 比べた案 | 測定した場面と回数 | 結果 | 費用 |
| --- | --- | --- | --- |
| 利用者の発言の原文を戻す（新しい順に 9,000 文字まで） | 24個の細目＋訂正3＋禁止3（計 27項目）、compact 1回目・2回目、会話約 122,000 トークンの場面（各 N=3） | 何も入れない実行も誤り 0件で差なし。要約が細目を全部残した | 2,808〜5,280 文字 |
| 読んだファイルを読み直させる（手順書ファイルを読み直すまで tool を止める実行、または読み直しを勧める文を入れる実行） | 3場面（各 N=3）。手順書ファイルは22回すべてで compact 後の `file` attachment に入っていなかった | 何も入れない実行も 9/9 回で自分で読み直し、全実行で要件 12/12（または 14/14）を満たして差なし | 勧める文は 325 文字。tool を止める実行は止めた呼び出し 0〜1回 |
| 最後のツール入力を戻す | 3場面（N=3、N=8、N=3） | 何も入れない実行も誤り 0件で差なし（ただし何も入れない実行の 1/8 回では要約が9項目中1項目しか残さず、モデルが会話の記録 JSONL を検索して自力で回復した） | 593 文字 |
| 承認と制約が続くという注記を入れる | 3場面（何も入れない実行 9回、注記を入れた実行 9回） | どちらも 9/9 回で違反 0件、差なし。要約が制約を毎回残した | 300 文字 |

PreCompact で要約を作るモデルに指示する案は、規則については効果があった（要約が15規則を残した回数が 2/12 から 6/6、違反平均 1.5件、N=6。利用者の発言の細目は何も入れない実行も指示ありも 28/28 で差なし）。しかし要約が約 4,600 文字長くなり compact 直後の入力トークンが約 +1,800 トークン増えるため、compact の直後に全文を入れ直す方式を採り、PreCompact での指示は採らなかった。

なお、差が出なかった4つは「この場面では何も入れない実行に損失が出なかった（または天井だった）ため効果を測れなかった」という結果であり、あらゆる場面で効果が無いと証明したわけではない。

## 測れなかったこと・限界

- 効果の測定は1つのモデル（`sonnet`）だけであり、会話も比較的短い（compact 前の文脈は約 37,000〜57,000 トークン）。
- 測定用に作ったプロジェクト指示にあたる文（約 2,200 文字、英語の規則15個）は、実物のプロジェクト指示（6,000〜10,000 文字）より短い。
- 利用者の既定の環境では auto compact を測っていない。また、既定の環境で規則が残りやすかった原因の切り分けも未実施である。
- 15個の規則のうち4個（禁止語「just/simply/basically」・絵文字・ダッシュ・「task」禁止）はモデルがもともと破らないため、この場面では差を測れていない。時刻の規則は規則文の解釈（UTC 併記）による違反が全文を入れ直す実行にも残った。

## 同じ検証をやり直す方法

### 仕組みの再確認

1. 会話の最初の利用者メッセージにプロジェクト指示（または測定用の長い規則文）を入れる。
2. その規則に関係しない短い作業を数回行った後に `/compact` を実行する。
3. 会話の記録（transcript の JSONL）で、最初のメッセージの原文が残っているかと要約の内容を確認し、モデルに各項目の内容を答えさせる。

### 入れ直しの効果の再確認

1. `claude -p --input-format stream-json` と `--setting-sources project` を使い、機械的に検査できる規則群を最初のメッセージに入れた場面を作る。
2. 何も入れない実行と、`SessionStart`（`compact`）の hook で規則の全文を出力する実行をそれぞれ複数回走らせる（auto compact を試すときは `CLAUDE_CODE_AUTO_COMPACT_WINDOW` と `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` を設定する）。
3. 会話の記録 JSONL で `compact_boundary` の数と `hook_additional_context` の有無を確認し、compact 後の返信の違反数と最初の応答の入力トークンを比べる。
