# 開発の説明を図で示す作り方

- 3つ以上の部品や人の関係、画面や状態をまたぐ流れ、変更の前と後、順序のあるやりとりは、最初から図で説明し、文章は図ごとの要点1行にする。2つのものの関係、分岐の無い短い手順、1つの値は文章で書く。
- 形の一覧は目安で、見せたいことに合わなければほかの形を選ぶ。
- 数の比較、市場、事業の枠組みの図は、同じリポジトリの plugin「business-figures」の skill で選ぶ。

## 選ぶ順

1. その図で言いたいことを1文に決める（例：「決済の失敗は API と外部の決済サービスの間で起きる」）。
2. その1文が何を見せるかを、下の分類から決める。
3. [references/figures.html](references/figures.html) のその分類の図から形を選ぶ。形から先に決めない。
4. 描き方は、次の順で最初に当てはまるものを使う。
   1. Artifact の側にその形の描き方があればそれを使う。Artifact の側とは、Artifact の tool が作れる種類と、その時点の skill の一覧にある Artifact や図の skill（artifact-diagramming など）である。直す元の資料に同じ図があれば、それも使う。
   2. figures.html の図に Mermaid の行があり、置き場所が Mermaid を表示できるとき（GitHub の Markdown、PR の説明、issue）は、その種類の Mermaid で書く。文書の中の図が差分で読め、直しやすいため。
   3. どちらも無ければ、figures.html の見本を写して svg で描く。

figures.html には38種の図が、名前、形（何を、どの位置や線や色で描くか）、使う場面、描ける Mermaid の種類、最小の svg で並ぶ。名前だけで形が浮かばない図は、その図の `<figure>` を読んで形を写す。見本の svg は形を示すためのもので、描く手段は決めない。

## 分類

| 分類 | 見せること |
|---|---|
| 構造 | 何がどの部品でできていて、境界と依存の向きはどうか |
| やりとり | 誰が誰に、どの順で、何を頼み、何が返るか |
| 状態と手順 | 状態がどう変わり、処理がどこで分かれるか |
| データ | 何がどこに入り、どう流れ、どう関係するか |
| 配置 | どこで動き、どの境界をまたいで通信するか |
| 時間 | いつ何が起き、どの順で進むか |
| 変更 | 前と後で何が変わり、どの順で移すか |
| 性能と信頼性 | どこで時間や資源を使い、どれだけ失敗してよいか |
| 判断 | 案をどの観点で比べ、何を選ぶか |

役割ごとの手順（スイムレーン）、期間の計画（ガント）、条件の分かれ（判断の木）、原因の分解（なぜの木、フィッシュボーン）、量の流れ（Sankey）は、business-figures の figures.html にある形を使う。

## 描き方の決まり

- 1枚の図の四角は6つまでにし、四角の中の文字は部品の名前と数語にする。超えるときは、範囲を分けた図にするか、下の連作にする（四角を詰めると、どこを見ればよいかが読み手に分からなくなるため）。
- どの四角も、ほかの四角と矢印か入れ子でつなぐ。つながらない四角は描かない。
- 矢印には、何を渡すか（呼び出し、データの名前、方式）を書く。同期の呼び出しは実線、応答や非同期は点線にする。
- 部品が3つ以上増える構成や、3段階以上の移行は、同じ配置の図を段階ごとに並べ、各段階で1つずつ足す連作にする。
- 変更の前と後は同じ配置で並べ、足すものを緑、消すものを赤の点線、変えるものを太線にして、変わらない所には印を付けない。
- 状態の図は、先に状態と遷移（出来事と条件）を一覧にして抜けと行き止まりを確かめてから描く。
- 図の中に文を詰めない。文は図の下の要点1行か、畳んだ詳細に置く。
